# Research: Botón único de promoción a producción

**Feature**: `specs/20261005-140934-promover-todo-produccion/spec.md`

## 1. Cómo agrupar los 3 workflows de GitHub Actions ya gateados sin duplicar código

- **Decision**: agregar el trigger `workflow_call: {}` a los tres workflows existentes (`migraciones-cloud.yml`, `deploy-infraestructura-vps.yml`, `publicar-flows-kestra.yml`), y cambiar la condición `if` del job `production` de cada uno de `github.event_name == 'workflow_dispatch'` a `github.event_name == 'workflow_dispatch' || github.event_name == 'workflow_call'`. El nuevo workflow `promover-todo-a-produccion.yml` los invoca con `uses: ./.github/workflows/<archivo>.yml` + `secrets: inherit`.
- **Rationale**: `workflow_call` es el mecanismo nativo de GitHub Actions para que un workflow invoque los jobs de otro sin copiar sus steps — ya se usa el patrón "no construir nada custom, usar lo nativo" en este repo (ver `research.md` de `20261003-105444-cicd-staging-produccion` §6). Dentro de una corrida disparada por `workflow_call`, `github.event_name` vale `workflow_call`, no `workflow_dispatch` — sin este ajuste el job `production` se saltearía (`if` evaluaría falso) y el botón único no haría nada.
- **Alternatives considered**: (a) Un script/Action custom que dispare los 3 `workflow_dispatch` por API y espere su resultado (`gh workflow run` + polling) — descartado: más complejo, introduce una dependencia de polling con límites de rate, y no hay forma limpia de propagar el fallo de un sub-workflow al resultado del workflow padre sin construir ese polling a mano. (b) Fusionar los 3 workflows en uno solo con jobs condicionales — descartado: rompe la independencia de despliegue ya establecida (Principio IV de la constitución) y complica los `paths` de cada trigger de `staging`.

## 2. Un mecanismo falla, los demás no deben bloquearse

- **Decision**: cada job invocado vía `workflow_call` en `promover-todo-a-produccion.yml` corre sin `needs` entre sí (los 4 jobs — 3 reusables + Refine — son independientes, todos se disparan en paralelo). GitHub Actions ya no cancela jobs hermanos cuando uno falla, salvo que el workflow use `strategy.fail-fast` (no aplica a jobs independientes) — el comportamiento por defecto ya cumple FR-006 sin configuración adicional.
- **Rationale**: evita acoplar la promoción de un mecanismo a que otro haya tenido éxito, que es justo el escenario del edge case 3 de la spec.
- **Alternatives considered**: ninguna — es el comportamiento nativo por defecto.

## 3. Cómo promover Refine/Vercel sin depender de un plan de pago ni de un token nuevo si es evitable

- **Decision**: introducir una rama `production` en el repo (creada una sola vez, apuntando al commit actual de `main`), y cambiar en Vercel qué rama usa la **Production Branch** del proyecto — en la práctica, esto se resuelve reasignando el `gitBranch` del dominio de producción del proyecto (`PATCH /v9/projects/{id}/domains/{domain}` con `{"gitBranch": "production"}`, confirmado como endpoint real de la API REST de Vercel) de `main` (implícito, es el default del proyecto) a `production`. El paso de "promover" en el workflow nuevo es, entonces, un `git push origin main:production` (fast-forward) desde un job con `permissions: contents: write` — un push explícito, no builds ni CLI de Vercel involucrados.
- **Rationale**: no requiere instalar el CLI de Vercel en CI ni generar un `VERCEL_TOKEN` nuevo — el repo ya está conectado a Vercel por la integración nativa de GitHub, que sigue reaccionando a cualquier push a cualquier rama (generando su propio deploy, igual que hoy genera uno para `main`); solo cambia cuál de esos deploys queda aliaseado al dominio de producción. `main` pasa a comportarse como el "staging persistente" que la spec pide (ya tiene URL estable: `estudio-contable-automation-git-main-macn.vercel.app`), sin tocar su ciclo de push automático actual (cumple la restricción de no gatear dev→staging).
- **Alternatives considered**: (a) `vercel promote <deployment-url>` vía CLI/API, re-apuntando el alias de producción al deployment exacto que ya corrió para `main` sin rebuildear — más preciso (evita drift entre lo que se validó y lo que se publica) pero requiere `VERCEL_TOKEN` como secret nuevo en el repo y el CLI de Vercel instalado en el runner; se deja documentado como mejora futura si el enfoque de branch resulta insuficiente, no se implementa en esta spec para no sumar una credencial nueva sin necesidad. (b) Cambiar la "Production Branch" desde el dashboard de Vercel en vez de la API — funcionalmente equivalente, requiere una intervención manual humana de todos modos (ver §4); se documenta como alternativa si la llamada a la API no estuviera disponible en la práctica.
- **Confirmado en vivo (2026-10-05)**: proyecto real inspeccionado vía API de Vercel (autenticado) — `estudio-contable-automation`, cuenta personal (sin Team), dominios actuales `estudio-contable-automation.vercel.app` / `-macn.vercel.app` / `-git-main-macn.vercel.app`, variables de entorno ya separadas por `target` (`production` vs `preview`) sin scoping por rama — no hace falta tocarlas, el deploy de `main` ya usaría el set `preview` (el de staging) en cuanto `main` deje de ser la rama de producción.

## 4. Qué requiere intervención humana de todos modos (no resuelto por el código de esta spec)

- **Decision**: crear la rama `production` y reasignar el `gitBranch` del dominio de producción son operaciones que se ejecutan una sola vez, al implementar esta spec — no son parte del workflow recurrente. Documentado en `quickstart.md` como pasos de bootstrap explícitos, a ejecutar solo con confirmación del usuario (regla de operación ya vigente, ver Assumptions de la spec).
- **Rationale**: son cambios de configuración sobre un sitio ya en producción — quedan fuera de lo que el propio workflow automatiza, consistente con que esta spec no introduce ningún control automático de aprobación nuevo.

# Research: Botón único de promoción a producción

**Feature**: `specs/20261005-140934-promover-todo-produccion/spec.md`

## 1. Cómo agrupar los 3 workflows de GitHub Actions ya gateados sin duplicar código

- **Decision**: agregar el trigger `workflow_call: {}` a los tres workflows existentes (`migraciones-cloud.yml`, `deploy-infraestructura-vps.yml`, `publicar-flows-kestra.yml`), y cambiar la condición `if` del job `production` de cada uno de `github.event_name == 'workflow_dispatch'` a `github.event_name == 'workflow_dispatch' || github.event_name == 'workflow_call'`. El nuevo workflow `promover-todo-a-produccion.yml` los invoca con `uses: ./.github/workflows/<archivo>.yml` + `secrets: inherit`.
- **Rationale**: `workflow_call` es el mecanismo nativo de GitHub Actions para que un workflow invoque los jobs de otro sin copiar sus steps — ya se usa el patrón "no construir nada custom, usar lo nativo" en este repo (ver `research.md` de `20261003-105444-cicd-staging-produccion` §6). Dentro de una corrida disparada por `workflow_call`, `github.event_name` vale `workflow_call`, no `workflow_dispatch` — sin este ajuste el job `production` se saltearía (`if` evaluaría falso) y el botón único no haría nada.
- **Alternatives considered**: (a) Un script/Action custom que dispare los 3 `workflow_dispatch` por API y espere su resultado (`gh workflow run` + polling) — descartado: más complejo, introduce una dependencia de polling con límites de rate, y no hay forma limpia de propagar el fallo de un sub-workflow al resultado del workflow padre sin construir ese polling a mano. (b) Fusionar los 3 workflows en uno solo con jobs condicionales — descartado: rompe la independencia de despliegue ya establecida (Principio IV de la constitución) y complica los `paths` de cada trigger de `staging`.

## 2. Un mecanismo falla, los demás no deben bloquearse

- **Decision**: cada job invocado vía `workflow_call` en `promover-todo-a-produccion.yml` corre sin `needs` entre sí (los 4 jobs — 3 reusables + Refine — son independientes, todos se disparan en paralelo). GitHub Actions ya no cancela jobs hermanos cuando uno falla, salvo que el workflow use `strategy.fail-fast` (no aplica a jobs independientes) — el comportamiento por defecto ya cumple FR-006 sin configuración adicional.
- **Rationale**: evita acoplar la promoción de un mecanismo a que otro haya tenido éxito, que es justo el escenario del edge case 3 de la spec.
- **Alternatives considered**: ninguna — es el comportamiento nativo por defecto.

## 3. Cómo promover Refine/Vercel

- **Decision (original, descartada en la implementación)**: reasignar el `gitBranch` del dominio de producción del proyecto (`PATCH /v9/projects/{id}/domains/{domain}` con `{"gitBranch": "production"}`) para que la "Production Branch" efectiva pase de `main` a `production`, evitando así un secret nuevo.
- **Por qué se descartó, en vivo (2026-10-05)**: inspeccionado el proyecto real vía API de Vercel (autenticado), el único dominio registrado (`estudio-contable-automation.vercel.app`) tiene `gitBranch: null` — no apunta a `main` explícitamente, sigue lo que sea que el proyecto considere "Production" en ese momento. No existe ningún campo de API documentado para leer o cambiar la "Production Branch" del proyecto en sí (ni en el schema de `update_project`, ni en la documentación de Vercel buscada a fondo) — `gitBranch` en un dominio es para asignar ESE dominio a una rama puntual (p. ej. para un dominio custom de un ambiente de pruebas), no el lever correcto para cambiar qué rama es "producción" para todo el proyecto. Reasignarlo a ciegas sobre el único dominio real del sitio era adivinar sobre un sitio ya en vivo — se descartó sin ejecutarlo.
- **Decision (final)**: promover por `deployment_id`, vía el endpoint documentado `POST /v10/projects/{id}/promote/{deploymentId}` ("point production traffic to a given deployment", no rebuildea nada — ver `https://vercel.com/docs/rest-api/reference/endpoints/projects/point-production-traffic-to-a-given-deployment`). Nuevo script `scripts/promover-deployment-vercel.mjs`: busca el deployment más reciente de la rama `production` (`GET /v6/deployments?projectId=...&branch=production`, con reintento hasta que su `readyState` sea `READY`, timeout configurable) y lo promueve. El workflow sigue haciendo el `git push origin main:production` explícito primero (es lo que genera ese deployment), y después llama al script.
- **Rationale**: es el mecanismo que Vercel documenta explícitamente para este caso exacto ("Promote Vercel Preview Deployment to Production") — no depende de ninguna configuración de "Production Branch" ambigua ni de adivinar un campo de API. El costo real: sí hace falta un secret nuevo, `VERCEL_TOKEN` (token de acceso personal de Vercel, scope al proyecto si es posible) — **decisión explícita del usuario** (2026-10-05) de aceptar ese costo en vez de seguir buscando una forma sin secret, dado que no existe una alternativa igual de confiable sin él. También requiere `VERCEL_PROJECT_ID` (no es secreto, pero se guarda igual como secret de Environment por simplicidad, mismo patrón que los demás mecanismos).
- **Alternatives considered**: (a) `vercel` CLI (`vercel promote <url> --yes --timeout 5m --token ...`) en vez de llamar la API REST directo — descartado: instalar el CLI en el runner es una dependencia más para un caso que la API cubre con dos llamadas HTTP simples, y el repo ya tiene el patrón de scripts Node pequeños y testeados (`verificar-staging-exitoso.mjs`) en vez de invocar CLIs de terceros cuando alcanza con `fetch`. (b) Reasignar `gitBranch` del dominio igual, confiando en que funcione como "Production Branch" — descartado por el motivo de arriba, no verificado ni documentado.
- **main como staging persistente**: sigue siendo cierto sin que haga falta ningún cambio de "Production Branch" — `main` ya tiene su URL estable (`estudio-contable-automation-git-main-macn.vercel.app`) hoy, independientemente de qué rama termine siendo la production real; no se toca su ciclo de push automático (cumple la restricción de no gatear dev→staging).

## 4. Qué requiere intervención humana de todos modos (no resuelto por el código de esta spec)

- **Decision**: crear la rama `production` (ya hecho, 2026-10-05, por el usuario directamente vía `git push` tras el bloqueo del clasificador de permisos) y crear los secrets `VERCEL_TOKEN`/`VERCEL_PROJECT_ID` en el Environment `promover-todo-a-produccion` del repo derivado son operaciones de una sola vez — no son parte del workflow recurrente. El token lo genera y carga el usuario directamente (un agente no debe generar ni ver el valor de un token de acceso real).
- **Rationale**: son cambios de configuración/credenciales sobre un sitio ya en producción — quedan fuera de lo que el propio workflow automatiza, consistente con que esta spec no introduce ningún control automático de aprobación nuevo.
